ZTPD-1542 修复验证 — 测试要点

Case: ZTPD-1542 修复版本: v9m.2.23 (Task 5588) 环境: ytlc-test 日期: 2026-06-22
这份文档给测试人员: 直接复制 SQL 跑,按步骤填结论。背景知识可以不看,执行清单必须做完。

0. 一句话背景(可选读)

修复前,系统对"零金额发票"(只有 payment, 无费用项) 不写 ITEMISED_FEE,且标 IRBM_STATE='N'(无需通知),不提交 IRBM。 v9m.2.23 修复后,即使费用为 0,系统也自动写 ITEMISED_FEE 占位行,并走完整 IRBM 校验流程(IRBM_STATE 应分布在 A/C/F)。 本验证的目的:确认 ytlc-test 在 v9m.2.23 上,6.16 之后新生成的 Type=7 零金额发票不再有上述 bug 行为。

1. 验证范围 — 四条件必须同时满足

#条件SQL 体现
1CREATE_DATE >= '2026-06-16'修复部署日之后生成
2零费用逻辑:RECV_CHARGE <> 0 且当月无 ACCT_ITEM用户原 SQL 核心条件
3E_INVOICE_TYPE = '7' (Regular Invoice)BILL_FLOW 体系后付费
4IRBM_STATE <> 'N' 且 E_INVOICE_ITEMISED_FEE 有行修复后期望

2. 执行步骤

Step 1 — 确认 ytlc-test 已部署 v9m.2.23

方法任选一种(任一能确认即可):

  • 查部署日志 / release note
  • 问 R&D(Chai)或 Ops
  • 查 CC.SYS_VERSION 或类似版本表(如果有)
关键前提: 如果 ytlc-test 不是 v9m.2.23,后面所有验证都无效,先停下来确认版本。

Step 2A — 反向验证(必跑)

目的: 6.16 之后,Type=7 零金额发票,还有多少 IRBM_STATE='N'。

-- Step 2A: 反向验证
-- 期望: dirty_count = 0 (修复后系统不应再标 N)
SELECT COUNT(*) AS dirty_count
FROM CC.E_INVOICE A
INNER JOIN CC.ACCT_ATTR_VALUE B ON A.ACCT_ID = B.ACCT_ID
INNER JOIN CC.BILL E ON A.E_INVOICE_ID = E.E_INVOICE_ID
WHERE B.ATTR_ID = '907207'
  AND A.IRBM_STATE = 'N'
  AND A.E_INVOICE_TYPE = '7'
  AND B.ATTR_VALUE NOT IN ('TESTLINE')
  AND A.CREATE_DATE >= DATE '2026-06-16'
  AND E.RECV_CHARGE <> 0
  AND NOT EXISTS (
      SELECT 1
      FROM CC.ACCT_ITEM C
      INNER JOIN CC.BILLING_CYCLE D ON C.BILLING_CYCLE_ID = D.BILLING_CYCLE_ID
      WHERE A.ACCT_ID = C.ACCT_ID
        AND D.INVOICE_DATE >= DATE '2026-06-16'
  );
结果判定
dirty_count = 0通过 修复有效,继续 Step 2B
dirty_count > 0不通过 仍有脏数据 → 检查 Step 1 版本,确认是否真是 v9m.2.23

Step 2B — 正向验证:IRBM_STATE 分布(必跑)

目的: 6.16 之后,Type=7 零金额发票,IRBM_STATE 的实际分布。

-- Step 2B: 正向分布
-- 期望: N = 0, 全部分布在 A / C / F(走完 IRBM 流程)
SELECT A.IRBM_STATE, COUNT(*) AS cnt
FROM CC.E_INVOICE A
INNER JOIN CC.ACCT_ATTR_VALUE B ON A.ACCT_ID = B.ACCT_ID
INNER JOIN CC.BILL E ON A.E_INVOICE_ID = E.E_INVOICE_ID
WHERE B.ATTR_ID = '907207'
  AND A.E_INVOICE_TYPE = '7'
  AND B.ATTR_VALUE NOT IN ('TESTLINE')
  AND A.CREATE_DATE >= DATE '2026-06-16'
  AND E.RECV_CHARGE <> 0
  AND NOT EXISTS (
      SELECT 1
      FROM CC.ACCT_ITEM C
      INNER JOIN CC.BILLING_CYCLE D ON C.BILLING_CYCLE_ID = D.BILLING_CYCLE_ID
      WHERE A.ACCT_ID = C.ACCT_ID
        AND D.INVOICE_DATE >= DATE '2026-06-16'
  )
GROUP BY A.IRBM_STATE
ORDER BY cnt DESC;
值含义期望
A待校验修复后短期可见,正常
CPortal 校验通过正常
FIRBM 校验通过期望占绝大多数
N无需通知必须 = 0
B / D / EPortal 失败 / 网络异常 / IRBM 失败个别可接受,大量需查

Step 2C — ITEMISED_FEE 写入验证(必跑)

目的: 修复后,Type=7 零金额发票(非 N)的 ITEMISED_FEE 是否被自动写入。

-- Step 2C: ITEMISED_FEE 写入验证
-- 期望: fee_count > 0 的发票占绝大多数
SELECT
  CASE WHEN f.fee_count IS NULL THEN 0 ELSE f.fee_count END AS fee_count,
  COUNT(*) AS invoice_count
FROM CC.E_INVOICE A
INNER JOIN CC.ACCT_ATTR_VALUE B ON A.ACCT_ID = B.ACCT_ID
INNER JOIN CC.BILL E ON A.E_INVOICE_ID = E.E_INVOICE_ID
LEFT JOIN (
  SELECT E_INVOICE_ID, COUNT(*) AS fee_count
  FROM CC.E_INVOICE_ITEMISED_FEE
  GROUP BY E_INVOICE_ID
) f ON f.E_INVOICE_ID = A.E_INVOICE_ID
WHERE B.ATTR_ID = '907207'
  AND A.E_INVOICE_TYPE = '7'
  AND B.ATTR_VALUE NOT IN ('TESTLINE')
  AND A.CREATE_DATE >= DATE '2026-06-16'
  AND A.IRBM_STATE <> 'N'
  AND E.RECV_CHARGE <> 0
  AND NOT EXISTS (
      SELECT 1 FROM CC.ACCT_ITEM C
      INNER JOIN CC.BILLING_CYCLE D ON C.BILLING_CYCLE_ID = D.BILLING_CYCLE_ID
      WHERE A.ACCT_ID = C.ACCT_ID
        AND D.INVOICE_DATE >= DATE '2026-06-16'
  )
GROUP BY f.fee_count
ORDER BY invoice_count DESC;
结果判定
fee_count > 0 的 invoice_count 占绝大多数通过
fee_count = 0 占多数不通过 系统未自动补 ITEMISED_FEE 行

Step 2D — 端到端正向验证(必跑,最关键)

目的: 同时满足 IRBM_STATE <> 'N' 且 ITEMISED_FEE 有行的发票占比。

-- Step 2D: 端到端正向验证
-- 期望: both_ok = total_invoice (100%)
SELECT
  COUNT(*) AS total_invoice,
  SUM(CASE WHEN A.IRBM_STATE <> 'N' THEN 1 ELSE 0 END) AS irbm_not_n,
  SUM(CASE WHEN f.E_INVOICE_ID IS NOT NULL THEN 1 ELSE 0 END) AS has_itemised_fee,
  SUM(CASE WHEN A.IRBM_STATE <> 'N' AND f.E_INVOICE_ID IS NOT NULL THEN 1 ELSE 0 END) AS both_ok
FROM CC.E_INVOICE A
INNER JOIN CC.ACCT_ATTR_VALUE B ON A.ACCT_ID = B.ACCT_ID
INNER JOIN CC.BILL E ON A.E_INVOICE_ID = E.E_INVOICE_ID
LEFT JOIN CC.E_INVOICE_ITEMISED_FEE f ON f.E_INVOICE_ID = A.E_INVOICE_ID
WHERE B.ATTR_ID = '907207'
  AND A.E_INVOICE_TYPE = '7'
  AND B.ATTR_VALUE NOT IN ('TESTLINE')
  AND A.CREATE_DATE >= DATE '2026-06-16'
  AND E.RECV_CHARGE <> 0
  AND NOT EXISTS (
      SELECT 1 FROM CC.ACCT_ITEM C
      INNER JOIN CC.BILLING_CYCLE D ON C.BILLING_CYCLE_ID = D.BILLING_CYCLE_ID
      WHERE A.ACCT_ID = C.ACCT_ID
        AND D.INVOICE_DATE >= DATE '2026-06-16'
  )
GROUP BY ()
HAVING COUNT(*) > 0;
结果判定
total_invoice = both_ok完全修复
irbm_not_n < total_invoice部分发票还停留在 N
has_itemised_fee < total_invoice部分发票未自动写 ITEMISED_FEE
both_ok < total_invoice部分发票任一条件不满足

触发条件:如果上面 4 个 SQL 跑出来 total_invoice = 0 或数据很少(比如 < 10 条),意味着 ytlc-test 没有自然产生的"零费用 + 收款"样本,这不是修复有效,是测试环境无数据。必须主动构造:

  4. 查 CC.E_INVOICE_ITEMISED_FEE 是否有自动写入的行

  • 问 R&D(Chai)拿 v9m.2.23 的 R&D 测试用例

5. 常见问题

Q1: 跑出来 total_invoice = 0 怎么办?

说明 ytlc-test 在 6.16 之后没有自然产生的"零费用 + 收款"样本。直接进 Step 3 主动构造,不要下"修复有效"的结论。

Q2: 反向 dirty_count = 0 但正向仍有 N 状态?

可能性: 2A SQL 因为其他 JOIN 条件把数据过滤掉了,实际有 N 但没被捞到。改用更宽松的 WHERE 重跑,或直接查 CC.E_INVOICE 主表:

SELECT COUNT(*)
FROM CC.E_INVOICE
WHERE IRBM_STATE = 'N'
  AND E_INVOICE_TYPE = '7'
  AND CREATE_DATE >= DATE '2026-06-16';

Q3: ITEMISED_FEE 表关联匹配率低?

不要用 CC.E_INVOICE_GEN_LOG 关联,那表 EMPTY_BILL='Y' 全表分布,匹配不上。
正确关联路径: E_INVOICE.E_INVOICE_ID → E_INVOICE_ITEMISED_FEE.E_INVOICE_ID。

Q4: ytlc-test 不是 v9m.2.23?

停下,联系 R&D / Ops 确认部署时间,部署完重新从 Step 1 开始。不要基于错误版本下结论。
